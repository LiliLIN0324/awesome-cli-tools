# 如何评测一个 CLI / How to Evaluate a CLI

> 目的：用一套**可重复**的方法判断某个命令行工具值不值得进你的工具箱，
> 而不是靠一篇博客的截图。本文件也是本仓库收录条目的判断依据。

## 评测顺序（先淘汰，再比较）

按「淘汰成本从低到高」排序。任何一步失败就直接结束，不必继续。

### 第 1 步：它到底解决什么问题（30 秒）

- 一句话能否说清？说不清通常意味着它是平台而不是工具。
- 它替换的是哪个**你已经在用**的东西？如果答案是「没有对应的旧工具」，
  警惕伪需求。
- 去 README 找「Alternatives」小节。作者自己承认的替代品列表，
  比任何评测都诚实。

### 第 2 步：安装与卸载（5 分钟）

```bash
# 只在这个 shell 里试，先别污染全局
# 优先选能「临时运行」的方式
npx -y some-tool --help
uvx some-tool --help
docker run --rm some/image:tag --help
```

判据：

- 能否**一条命令**装好？需要手动改 `PATH`、装编译链、或先装运行时吗？
- 能否**干净卸载**？会往家目录写多少东西？（`~/.config/x` vs 到处撒）
- 有没有**单一二进制**版本？有的话跨机器复制成本极低。
- 卸载/清理路径在文档里写了吗？没写就是一个红灯。

### 第 3 步：默认行为是否合理（10 分钟）

不看文档，只敲 `<tool> --help`，然后试着完成最常见的那件事。

- 默认值是「安全且有用」的，还是「什么都不做」的？
- 有没有危险的默认行为（自动上传、自动删除、自动提交）？
- `--help` 是否完整？还是文档写「详见官网」但官网又让你看 `--help`？

### 第 4 步：可脚本化程度（15 分钟）

这是本仓库最看重的一步。

```bash
# 1) 机器可读输出
tool list --json | jq '.items[0]'

# 2) 颜色可控（不应污染管道）
tool list | cat -v | head          # 用 --color=never 后应无 ANSI 码
NO_COLOR=1 tool list | cat -v | head

# 3) 退出码语义
tool check good-input;  echo $?    # 期望 0
tool check bad-input;   echo $?    # 期望非 0，且不是 0

# 4) 幂等与 dry-run
tool apply --dry-run
tool apply && tool apply           # 第二次应无变化或明确报「已是最新」

# 5) 非 TTY 环境
tool list < /dev/null               # 不应卡在交互提示上
```

任一项不通过，都要在收录时写进「注意事项」。

### 第 5 步：错误信息质量（5 分钟）

故意写错参数，看它怎么回复：

- 是「unknown flag: --nmae」还是只有一行 usage？
- 有没有指出**可能想输入的是 `--name`**？
- 有没有指出「你漏了必填的 X」？

好的错误信息省下的时间，长期看比性能差距重要得多。

### 第 6 步：维护活跃度（5 分钟）

```bash
# 有 gh 的话最省事
gh repo view owner/tool --json pushedAt,archived,licenseInfo,openIssues

# 没有 gh 就看 release 页面时间线
# 关键点：
#   - 最近一次 release 距今多久？（> 18 个月要警惕）
#   - issue 是「有回复但没修」还是「无人理会」？
#   - 安全类 issue 的处理速度
```

### 第 7 步：许可证（2 分钟）

- 有 `LICENSE` 文件吗？内容是 SPDX 里能识别的常见许可吗？
- 是 BUSL / SSPL / Elastic License 这类**非 OSI 开源**许可吗？
  如果是，在条目里必须显式标注（例如 Terraform、n8n）。
- 「源码可见但禁止生产使用」的许可要格外注意，不要当成开源。

## 快速打分表

每项 0–2 分（0 不满足 / 1 部分满足 / 2 满足），总分 16：

| 项 | 判据 | 分 |
| --- | --- | --- |
| 问题清晰 | 一句话能说清要解决什么 | |
| 安装 | 一条命令装好且能干净卸载 | |
| 默认值 | 不需要大量 flag 就能干活 | |
| 机器可读输出 | 有 `--json` / `--porcelain` 等 | |
| 颜色可控 | 遵守 `NO_COLOR` / `--color` | |
| 退出码 | 0/非 0 语义正确 | |
| 幂等/dry-run | 危险操作有预览 | |
| 错误信息 | 能指出错在哪、怎么修 | |
| 文档一致 | `--help` 与文档不矛盾 | |
| 活跃度 | 18 个月内有发布 | |
| 许可证 | 明确且允许你的使用场景 | |
| 家目录整洁 | 配置集中、遵循 XDG | |
| 平台覆盖 | 至少两个平台的官方支持 | |
| 无强制遥测 | 或可关闭且已披露 | |
| 可组合 | 能与常见 Unix 工具串起来 | |
| 专注 | 一个工具做一件事 | |

**解读**：≥ 13 分可以直接进你的日常工具箱；9–12 分值得收录但要在条目里
注明代价；≤ 8 分除非不可替代，否则不建议引入。

## 反模式清单

- ❌ 因为「截图好看」就换工具。截图不体现退出码。
- ❌ 只看 star 数。star 是兴趣指标，不是质量指标。
- ❌ 一次换掉多个工具，出问题分不清是谁导致的。
- ❌ 忽略许可证直到要上线前一周。
- ❌ 把一个交互式 TUI 引入必须自动化的流程。
